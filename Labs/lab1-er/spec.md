# Spec: Завдання 1 — ER-модель онлайн-бібліотеки з підпискою

## Намір та контекст домену

Описати дані онлайн-бібліотеки з підпискою як ER-модель: сутності, атрибути,
зв'язки й кардинальності. Модель стане основою для наступних завдань —
вимог (Lab2), взаємодії (Lab3), процесу (Lab4) і архітектури (Lab5).

**Домен:** онлайн-бібліотека з підпискою за моделлю Bookmate (сервіс читання книг із каталогу за активним абонементом). Домен обрано самостійно, окремого стороннього проєкту-джерела немає.

**Причини вибору саме цього домену:**
1. **Збалансованість структури даних**: природно поєднує чистий зв'язок M:N (книга — жанр), асоціативну сутність із власними атрибутами (книга — автор: роль, порядок) та ієрархічні зв'язки жанрів, що повністю відповідає академічним вимогам до ER-моделі без зайвих сполучних таблиць.
2. **Наскрізність для ланцюга робіт**: логіка тарифів, підписок і платежів забезпечує зовнішнього актора (платіжний шлюз) для Lab2/Lab3, процеси читання й оренди — для Lab4, а сервісні залежності — для Lab5.
3. **Реалістична й зрозуміла бізнес-модель**: прозорі сутності (каталог, абонементи, прогрес читання, відгуки) покривають повний життєвий цикл читача без штучних ускладнень.

## Сутності та атрибути

Ідентифікатори всіх сутностей — `string` (uuid). Це фіксується тут, у spec,
а не лише в DEFENSE.

**User** — користувач сервісу.
`user_id` (PK), `email` (унікальний), `display_name`, `password_hash`,
`locale`, `registered_at`, `status`.

**Plan** — тариф підписки.
`plan_id` (PK), `code` (унікальний), `title`, `price_cents`, `currency`,
`duration_days`, `max_concurrent_loans`.

**Subscription** — оформлена підписка користувача.
`subscription_id` (PK), `user_id` (FK), `plan_id` (FK), `started_at`,
`expires_at`, `status`, `auto_renew`.

**Payment** — платіж за підписку.
`payment_id` (PK), `subscription_id` (FK), `amount_cents`, `currency`,
`paid_at`, `method`, `status`, `external_txn_id` (унікальний).

**Book** — книга каталогу.
`book_id` (PK), `isbn` (унікальний), `title`, `publisher_id` (FK),
`published_year`, `language`, `page_count`, `description`.

**Publisher** — видавництво.
`publisher_id` (PK), `name`, `country`.

**Author** — автор.
`author_id` (PK), `full_name`, `country`, `bio`.

**BookAuthor** — асоціативна сутність «книга — автор».
`book_id` (FK), `author_id` (FK), `role`, `ordinal`.
Складений PK: (`book_id`, `author_id`, `role`). Поле `ordinal` — звичайний атрибут (порядок зазначення у виданні).

> **Рішення 2 (Структура ключів BookAuthor: вісь вибору A vs B та підтримка кількох ролей):**
> 
> Розглянуто вимогу предметної області: одна й та сама особа може одночасно виконувати кілька ролей для однієї книги (наприклад, автор тексту та ілюстратор, або перекладач і автор передмови). Складений ключ лише з двох полів `(book_id, author_id)` помилково забороняв би таку комбінацію через обмеження унікальності PK.
> 
> - **Варіант A (обрано):** природний складений первинний ключ із трьох полів `(book_id, author_id, role)` без штучного сурогатного ID. Атрибут `ordinal` залишається звичайним полем (порядок зазначення). Оскільки на `BookAuthor` не посилається жодна інша сутність, складений ключ є «безкоштовним» — він не призводить до розповзання триколонкових FK в інших таблицях, водночас точно моделює бізнес-правило: одна особа не може двічі мати одну й ту саму роль у тій самій книзі, але вільно може поєднувати різні ролі.
> - **Варіант B (альтернатива):** одно-польовий сурогатний PK `book_author_id` (uuid) + одно-польові FK (`book_id`, `author_id`) + складена трійка `UK (book_id, author_id, role)`. Цей варіант розглядався для однорідності форми PK, але відкинутий як надлишковий: сурогатний ID для чистої асоціації, на яку ніхто не посилається, не несе користі, якщо природний складений ключ `(book_id, author_id, role)` уже повністю й коректно вирішує задачу унікальності.

**Genre** — жанр, ієрархічний.
`genre_id` (PK), `code` (унікальний), `title`, `parent_genre_id` (FK на Genre).

**Loan** — видача книги користувачу.
`loan_id` (PK), `user_id` (FK), `book_id` (FK), `borrowed_at`, `due_at`,
`returned_at`. Стан позики (активна / повернена / прострочена) — похідний,
обчислюється з `returned_at` і `due_at`, не зберігається.

**Review** — відгук користувача про книгу.
`review_id` (PK), `user_id` (FK), `book_id` (FK), `rating`, `body`, `created_at`.
Пара (`user_id`, `book_id`) унікальна — один відгук на книгу від користувача.

**ReadingProgress** — прогрес читання.
`progress_id` (PK), `user_id` (FK), `book_id` (FK), `last_page`,
`updated_at`. Пара (`user_id`, `book_id`) унікальна. Відсоток прочитаного —
похідний від `last_page` і `Book.page_count`, не зберігається.

## Критерії прийняття

- [x] Кожна сутність має явно вказаний первинний ключ
- [x] Складені обмеження унікальності (пара `user_id`,`book_id` у Review і
      ReadingProgress) виражені в моделі позначкою `UK`, а не лише текстом
- [x] Усі ідентифікатори мають тип `string` (uuid) — без змішування `string` і `number`
- [x] Модель у 3НФ: немає часткових залежностей від складеного ключа і немає транзитивних залежностей
- [x] Похідні значення (`Loan.status`, `ReadingProgress.percent`) у моделі не
      зберігаються — обчислюються при читанні
- [x] Зв'язок Book — Genre подано як чистий M:N, без сполучної сутності
- [x] Зв'язок Book — Author подано як асоціативну сутність `BookAuthor`, бо зв'язок несе власні атрибути `role` і `ordinal`
- [x] Структура ключів `BookAuthor` відповідає Рішенню 2 (Варіант A): природний складений PK (`book_id`, `author_id`, `role`), що дозволяє особі поєднувати кілька ролей для однієї книги, з атрибутом `ordinal`
- [x] Назви атрибутів у spec і в `model/er.mmd` збігаються символ у символ
- [x] Кардинальності на діаграмі відповідають таблиці вище
- [x] Кардинальність самозв'язку `Genre` допускає жанр без батька (кореневі
      жанри) — `|o--o{`, а не `||--o{`
- [x] Немає сутностей, не з'єднаних із рештою моделі
- [x] Рендер у `renders/` збігається з `model/er.mmd`
- [x] Немає фізичної схеми БД (SQL DDL / ORM) — лише концептуальна модель

## Поза межами

- Фізична схема БД, індекси, типи СУБД — предмет курсу баз даних.
- Ролі та права доступу (RBAC) — не модельовано, у домені їх немає.
- Аудіокниги, офлайн-читання — не входять у поточну версію домену.
