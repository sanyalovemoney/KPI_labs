# Spec: Завдання 2 — Вимоги та варіанти використання

## Намір

Перекласти модель даних із Lab1 на структуровані вимоги: EARS, user stories,
Gherkin-сценарії та use case діаграму з матрицею трасування. Це місток між
«які дані» (Lab1) і «як вони взаємодіють» (Lab3).

## Актори

| Актор | Тип | Ціль |
|-------|-----|------|
| Читач | людина | обрати план, оплатити підписку, позичати й читати книги, лишати відгуки |
| Бібліотекар | людина | модерація відгуків, управління каталогом |
| Платіжний шлюз | зовнішня система | авторизація/скасування платежів |
| Поштовий сервіс | зовнішня система | листи підтвердження та сповіщення |

## Сутності з Lab1, якими оперують сценарії

Registration → User; Subscribe → Plan, Subscription, Payment;
BorrowBook / ReturnBook → Loan; ReadBook → Book, ReadingProgress;
SubmitReview → Review; ManageCatalog → Book, Author, Genre.

## Критерії прийняття

- [x] ≥2 типи акторів: людина + зовнішня система (у моєму разі 2+2)
- [x] Кожна вимога в EARS-формі (WHEN/WHILE/IF…THEN/UBIQUITOUS) з id REQ-NN
- [x] Матриця трасування many-to-many: один UC ≫ 1 вимоги, одна вимога ≫ 1 UC
- [x] ≥1 непокритий UC з поясненням, чому
- [x] Use case діаграма містить include, extend і узагальнення (generalization)
- [x] Хоча б 3 Gherkin-сценарії (позитивний + 2 альтернативних)
- [x] Всі імена сутностей у вимогах збігаються з ER-моделлю Lab1

## Що поза межами

Нефункціональні вимоги (SLA, безпека), рекомендаційна стрічка — домен Lab1 їх
не моделює, тому сюди я їх не домислюю.
