# Матриця трасування REQ ↔ UC

Статус: після аудиту. UC задаю **назвою**, не позицією в списку — в v1
нумерація матриці й діаграми роз'їхалась (AUDIT №1). Зв'язки багато-до-багатьох:
один REQ може покривати кілька UC, один UC закривати кілька REQ.

| REQ | User story | Покриття UC (за назвою) | Статус |
|-----|-----------|-------------------------|--------|
| REQ-01 реєстрація | — | UC-01 Зареєструватися (включає UC-02) | покрито |
| REQ-02 старт платежу | US-01 | UC-03 Оформити підписку, UC-04 Обробити платіж | покрито |
| REQ-03 успіх платежу | US-01 | UC-04 Обробити платіж, UC-03 Оформити підписку | покрито |
| REQ-04 умови позики | US-02 | UC-05 Позичити книгу, UC-06 Перевірити підписку і ліміт | покрито |
| REQ-05 прогрес читання | US-03 | UC-07 Читати книгу, UC-08 Зберегти прогрес читання | покрито |
| REQ-06 відгук | US-04 | UC-09 Залишити відгук | покрито |
| REQ-07 блокування при простроченні | US-02 | UC-06 Перевірити підписку і ліміт, UC-12 Нагадати про повернення | покрито |
| REQ-08 повернення | US-02 | UC-10 Повернути книгу | покрито |
| REQ-09 відхилений платіж | US-01 | UC-04 Обробити платіж | покрито |
| REQ-10 повторний відгук | US-04 | UC-09 Залишити відгук (разом з унікальністю пари Lab1) | покрито |
| REQ-11 повторний лист | — | — | **не покрито — свідомо** |
| REQ-12 модерація відгуків | US-05 | UC-11 Модерувати відгуки | покрито |

## Зворотний бік: навантаження UC

| UC | Закриває REQ |
|----|--------------|
| UC-03+UC-04 (підписка/платіж) | REQ-02, REQ-03, REQ-09 |
| UC-05+UC-06 (позика/перевірка) | REQ-04, REQ-07 |
| UC-07+UC-08 (читання/прогрес) | REQ-05 |
| UC-09 (відгук) | REQ-06, REQ-10 |

## Чому REQ-11 лишається непокритим

REQ-11 (повторний лист через 24 години) — фоновий процес без прямої
взаємодії з актором; на діаграмі use case він не має суб'єкта. Його носій
з'явиться в Lab5 (планувальник в AuthModule) — свідоме «не покрито» з
посиланням далі по ланцюгу, а не прогалина в аналізі.
