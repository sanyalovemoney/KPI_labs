# Матриця трасування REQ <-> UC (цикл v2)

Матриця покриває потік «Оформити підписку»: у циклі v2 тільки для нього є
EARS. UC задаю назвою, як вона стоїть у `model/usecase.puml`, а не позицією
в списку. Вимоги беру з `requirements.md`. Зв'язки перевіряю в обидва боки.

## Пряма трасованість: REQ -> Gherkin -> UC

| REQ | Коротка суть | Gherkin-сценарій | UC (за назвою) |
|-----|--------------|------------------|----------------|
| REQ-01 | активний `User` створює `Subscription` зі `status = "pending"` | S1, крок Given | Оформити підписку |
| REQ-02 | успіх шлюзу: `Payment` (success) і `Subscription` (active) зі строком з `Plan` | S1 | Оформити підписку; Обробити платіж |
| REQ-03 | відмова шлюзу: `Subscription.status = "canceled"`, без успішного `Payment` | S2 | Оформити підписку; Обробити платіж |
| REQ-04 | неактивний `User`: відмова до запиту в шлюз | S3 | Оформити підписку |
| REQ-05 | повторний `external_txn_id`: без другого `Payment`, без зміни `expires_at` | S4 | Оформити підписку; Обробити платіж |

## Зворотна трасованість: UC -> REQ

| UC | Актор | REQ, які закриває UC |
|----|-------|----------------------|
| Оформити підписку | Читач | REQ-01, REQ-02, REQ-03, REQ-04, REQ-05 |
| Обробити платіж | Платіжний шлюз | REQ-02, REQ-03, REQ-05 |

## Зв'язки багато-до-багатьох

- REQ-02, REQ-03 і REQ-05 закривають два UC: оформлення включає платіж, але
  платіж лишається окремою ціллю зовнішнього шлюзу.
- «Оформити підписку» закривають усі п'ять REQ: створення підписки, три
  відповіді шлюзу і відмова неактивному користувачу.
- «Обробити платіж» закривають три REQ: успіх, відмова і повтор.

Пари не 1:1: у прямій таблиці п'ять REQ дають вісім пар REQ -> UC, у
зворотній ті самі вісім. Розбіжностей немає.

## NFR не трасуються

| ID | Чому без UC |
|----|-------------|
| NFR-01 | продуктивність каталогу — властивість системи, не крок чиєїсь цілі |
| NFR-02 | час оплати — властивість інтерфейсу, а не UC платежу |
| NFR-03 | доступність — властивість сервісу в цілому |
| NFR-04 | TLS і bcrypt — вимога до транспорту й зберігання |
| NFR-05 | локалізація — властивість інтерфейсу |
| NFR-06 | браузери — властивість клієнтської частини |
| NFR-07 | пошта — деталь інтеграції, не ціль актора |

NFR описують якість системи в цілому. Прив'язка до UC зробила б вигляд, що
вимога належить одному сценарію, хоча вона діє на всі. Тому в матриці вони
стоять окремим блоком і не мають пари.

## UC поза циклом v2

| UC | Статус |
|----|--------|
| Зареєструватися | поза циклом v2 |
| Підтвердити email | поза циклом v2 |
| Позичити книгу | поза циклом v2 |
| Читати книгу | поза циклом v2 |
| Нагадати про повернення | поза циклом v2 |
| Повернути книгу | поза циклом v2 |
| Залишити відгук | поза циклом v2 |
| Модерувати відгуки | поза циклом v2 |

Ці UC не мають REQ циклу v2: їхні EARS-вимоги були в першій версії Lab2 і
лишилися в історії. Повторно їх не переписую, щоб не роздувати матрицю
зв'язками, які нічого не перевіряють. На діаграмі вони лишаються, щоб
модель не втратила цілі, які вже узгоджені з Lab1.

## Непокриті вимоги

Функціональних REQ без UC немає. Нетрасовані — NFR-01…NFR-07, причина в
блоці вище. Це свідоме «не покрито», а не прогалина: NFR перевіряються
тестами якості, а не сценарієм актора.
