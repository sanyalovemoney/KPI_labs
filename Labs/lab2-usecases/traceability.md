# Матриця трасування REQ <-> UC

UC задаю назвою, як вона стоїть у `model/usecase.puml`, а не позицією в списку:
звірка за назвою не залежить від нумерації. Вимоги беру з `requirements.md`.
Зв'язки багато-до-багатьох, тому перевіряю їх в обидва боки.

## Пряма трасованість: REQ -> US -> UC

| REQ | Коротка суть | US | UC (за назвою) |
|-----|--------------|----|----------------|
| REQ-01 | реєстрація створює `User` зі `status = pending` і ініціює лист підтвердження | US-01 | Зареєструватися; Підтвердити email; Надіслати сповіщення |
| REQ-02 | підтвердження за посиланням дає `User.status = active` | US-01 | Зареєструватися; Підтвердити email |
| REQ-03 | вибір `Plan` створює `Subscription` зі `status = pending` | US-02 | Оформити підписку |
| REQ-04 | успіх шлюзу: `Payment` (success) і `Subscription` (active) зі строком з `Plan` | US-02 | Обробити платіж; Оформити підписку |
| REQ-05 | відмова шлюзу: `Subscription.status = canceled`, без успішного `Payment` | US-02 | Оформити підписку; Обробити платіж |
| REQ-06 | позика в межах `Plan.max_concurrent_loans`: `Loan` з `due_at` = `borrowed_at` + 30 днів | US-03 | Позичити книгу |
| REQ-07 | збереження сторінки: запис `ReadingProgress` для пари (`user_id`, `book_id`) | US-04 | Читати книгу |
| REQ-08 | нагадування за 2 дні до `due_at` за порожнього `returned_at` | US-04 | Нагадати про повернення; Надіслати сповіщення |
| REQ-09 | повернення: `Loan.returned_at` = поточний момент | US-03 | Повернути книгу |
| REQ-10 | відгук: `Review`, рівно один на пару (`user_id`, `book_id`) | US-04 | Залишити відгук |
| REQ-11 | модерація: видалення запису `Review` | US-05 | Модерувати відгуки |
| REQ-12 | повторний лист підтвердження через 24 години, рівно один раз | — | — (не покрито — свідомо) |

## Зворотна трасованість: UC -> REQ

| UC | Актор | REQ, які закриває UC |
|----|-------|----------------------|
| Зареєструватися | Читач | REQ-01, REQ-02 |
| Підтвердити email | Читач (через include від «Зареєструватися»); Поштовий сервіс (через узагальнення) | REQ-01, REQ-02 |
| Оформити підписку | Читач | REQ-03, REQ-04, REQ-05 |
| Обробити платіж | Платіжний шлюз | REQ-04, REQ-05 |
| Позичити книгу | Читач | REQ-06 |
| Читати книгу | Читач | REQ-07 |
| Нагадати про повернення | Читач (через extend від «Читати книгу»); Поштовий сервіс (через узагальнення) | REQ-08 |
| Повернути книгу | Читач | REQ-09 |

| Модерувати відгуки | Бібліотекар | REQ-11 |
| Надіслати сповіщення | Поштовий сервіс | REQ-01, REQ-08 |

## Зв'язки багато-до-багатьох — звірка в обидва боки

- REQ-01 покриває три UC: «Зареєструватися», «Підтвердити email», «Надіслати
  сповіщення» — реєстрація запускає ланцюжок із листом підтвердження.
- UC «Зареєструватися» закривають два REQ: REQ-01 і REQ-02 — створення `User`
  та його активація належать одному потоку реєстрації.
- UC «Оформити підписку» закривають три REQ: REQ-03, REQ-04, REQ-05 —
  створення підписки, успіх платежу і відмова.
- UC «Обробити платіж» ділить із «Оформити підписку» вимоги REQ-04 і REQ-05:
  одні й ті самі REQ обслуговують два UC, бо платіж включений в оформлення,
  але винесений окремо через зовнішнього актора.
- UC «Надіслати сповіщення» збирає REQ-01 і REQ-08 — через два підтипи
  («Підтвердити email», «Нагадати про повернення»), у кожного свій тригер.

## Чому REQ-12 лишається непокритим

REQ-12 (повторний лист підтвердження через 24 години) — фоновий таймерний
процес: лист ініціює час, а не актор. Use case моделює ціль актора, а цю
вимогу ззовні ніхто не ініціює; штучний «актор-таймер» спотворив би діаграму,
та й у списку акторів `spec.md` такого немає. Носій вимоги (планувальник)
з'явиться в архітектурі Lab5 — це свідоме «не покрито» з посиланням далі по
ланцюжку, а не прогалина в аналізі.

## Непокриті UC

Непокритих UC немає: усі 11 варіантів використання з `model/usecase.puml`
закриті щонайменше однією вимогою. Єдина вимога без UC — REQ-12, причина
описана вище.
