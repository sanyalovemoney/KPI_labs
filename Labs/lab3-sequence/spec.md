# Spec: Завдання 3 — Sequence-діаграма позики книги

## Намір

Деталізувати динаміку UC-05 «Позичити книгу» з Lab2 — сценарій, у якому
зчеплено найбільше сутностей Lab1 (Subscription, Plan, Loan, Book) і який
Lab4 потім розкладе на бізнес-процес.

## Обраний UC

UC-05 «Позичити книгу», включає UC-06 «Перевірити підписку і ліміт» —
саме тут народжується блокування з REQ-07.

## Учасники та кроки

| Учасник | Роль | Покриття |
|---------|------|----------|
| Читач | актор Lab2 | ініціює |
| Web UI | інтерфейс | вхід/вихід |
| LoanService | сервіс позики | керує Loan |
| SubscriptionService | сервіс підписки | валідує Subscription/Plan |
| CatalogService | сервіс каталогу | доступ до Book |
| Repository (DB) | Data Access | збереження Loan |

Кроки: вибір книги -> створення позики -> перевірки (підписка, ліміт,
прострочення, чи книга є) -> запис Loan(due_at=now+30д) -> підтвердження.

## Критерії прийняття

- [x] Учасники — сервіси, що читають сутності з ER Lab1 (Loan, Subscription,
      Plan, Book), назви узгоджені з Lab5-майбутніми компонентами
- [x] Усі виклики мають return-повідомлення
- [x] alt: успішна позика / відмова (підписка неактивна) / відмова
      (прострочено) / відмова (ліміт)
- [x] opt: книга відсутня в каталозі
- [x] Крок «нагадати пізніше» — loop по активних Loan
- [x] Назви методів дієслівні й реалістичні: `createLoan`,
      `isSubscriptionActive`, `countActiveLoans` — по назві читається,
      що робить виклик

## Поза межами

Повернення книги — окремий сценарій, його динаміка в Lab4 як частини процесу
життєвого циклу позики.
