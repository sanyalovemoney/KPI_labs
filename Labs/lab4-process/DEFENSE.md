# Defense: Завдання 4 — Процес життєвого циклу підписки

## 1. Намір і критерії

Одна activity-діаграма (Mermaid flowchart, swimlanes читач/система/шлюз)
процесу «вибір плану -> оплата -> підписка -> позики/прострочення/повернення
-> поновлення». Критерії в `spec.md`: кожен вузол з входом і виходом,
guard-и дослівно з REQ, fork+join, ролі = актори Lab2, потоки = перевірки
Lab3, рівно одна форма.

## 2. Топ-3 розбіжності (знайдені й виправлені)

1. **Паралельна гілка без fork/join** — активація і лист послідовні, а
   spec вимагає join перед доступом → Commit:
   `lab4: fix - add fork/join for activation and welcome email`
2. **Вузол «Блокує позики» без виходу, немає повернення книги й
   завершальних станів** («діри», REQ-08 відсутній) → Commit:
   `lab4: fix - add return-book flow, unblock and terminal states`
3. **Guard «Результат платежу / так / ні» нечіткий і ретрай необмежений** —
   всупереч spec («до 3 спроб») → Commit:
   `lab4: fix - label payment guards with REQ refs, cap retries at 3`

## 3. Ключове рішення

Activity замість state-machine: процес багаторольовий і має паралельну
ділянку — ролі й fork/join нативні лише в activity. Статус позики як стан
не вів — Lab1 не зберігає його полем.

→ `adr/adr-001-activity-vs-state.md`
