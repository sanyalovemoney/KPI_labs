# ADR-001: Activity-діаграма, а не машина станів

## Контекст

Умова завдання 4 дозволяє обрати одну з двох форм для одного процесу.
Кандидат процесу — життєвий цикл підписки.

## Розглянуті альтернативи

1. **Машина станів (stateDiagram-v2)** — природна для одного об'єкта з
   малою кількістю станів (`Loan: активна -> прострочена -> повернена`).
   Але мій процес має три ролі — у state-machine ролі не виражаються
   взагалі; паралельні ділянки (активація підписки + лист) виглядали б
   неприродно. Плюс Lab1 свідомо не зберігає статус позики як поле —
   стан-машина вимагала б станів, яких модель даних не тримає.
2. **Activity (Mermaid flowchart + swimlanes)** — потоки керування,
   розгалуження з guard-ами, fork/join і ролі — саме те, що треба
   багаторольовому процесу.

## Рішення

Activity. Критерій вибору: процес багаторольовий **і** має паралельну
ділянку — обидва елементи в activity нативні, у машині станів їх довелось
би імітувати штучними переходами.

## Наслідки

- Життєвий цикл об'єкта Loan окремою діаграмою не показаний — його
  динаміка вже є в Lab3, дублювати заборонено («без двох нотацій»).
- Swimlane «Поштовий сервіс» в activity — це роль-актор з Lab2, а не
  окремий компонент; в Lab5 він стане компонентом-адаптером.
