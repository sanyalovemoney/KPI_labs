# Spec: Завдання 4 — Процес «Оформлення й використання підписки»

## Намір

Описати activity-діаграмою один бізнес-процес: життєвий цикл підписки від
вибору плану до повернення останньої книги. Процес деталізує UC-03/05 з Lab2
і потоково повторює перевірки з Sequence Lab3, але покладено (що система
робить), а не обмін повідомленнями.

## Форма

Activity (Mermaid flowchart зі swimlane-підграфами за ролями). Машину станів
відкинув — див ADR-001.

## Ролі (swimlanes)

Читач | Система | Платіжний шлюз

## Кроки й розгалуження

1. Читач обирає Plan; 2. підтверджує оплату; 3. Система створює Payment
(REQ-02); 4. Шлюз авторизує — **рішення**: успіх (REQ-03) / відхил (REQ-09,
повтор до 3 спроб, інакше процес повертається на крок 1).
5. **Паралельно (fork)** після успіху: а) активується Subscription
(`expires_at = started_at + duration_days`), б) Поштовий сервіс надсилає
лист; **join** — обидва кроки мають завершитись, перш ніж читач отримає
доступ.
6. Цикл читання: позика → (opt: прострочення REQ-07 → блокування нових
позик) → повернення (REQ-08) → **рішення**: `expires_at > now`? так —
нова позика (loop); ні — підписка добіга кінця, **join з читанням неможливий
до оплати поновлення**.

## Критерії прийняття

- [x] Кожен вузол має вхід і вихід; немає недосяжних станів і «дір»
- [x] ≥1 рішення (if/else) з підписаними умовами — умови дослівно з REQ-03/07/09
- [x] ≥1 паралельна гілка з коректним fork **і** join
- [x] Swimlanes відповідають акторам Lab2
- [x] Потоки повторюють перевірки Lab3 (підписка → прострочення → ліміт)
      без суперечностей
- [x] Рівно одна форма: activity; без дублюючої state-діаграми

## Поза межами

Скасування за умов GDPR, рефанди — немає вимог у Lab2.
