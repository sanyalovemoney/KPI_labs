# Специфікація Lab5: архітектура онлайн-бібліотеки з підпискою

## Навіщо це

Фінальна модель ланцюга: Lab1 дані → Lab2 вимоги → Lab3 взаємодія → Lab4
процес → тепер компоненти, інтерфейси й межі системи. Малюю UML Component
Diagram у PlantUML (як lab2–lab4). Три обіцянки попередніх лаб дістають тут
носіїв: REQ-12 (повторний лист підтвердження, фонова самокорекція) →
Планувальник, NFR-07 → MailPort, шлюзовий порт → PaymentGatewayPort
(ADR-001 lab4). Нових сутностей не вигадую: компоненти оперують тим, що вже
є в `er.mmd` і sequence Lab3.

## Модулі (трасування до Lab1..Lab4)

| Компонент | Роль | Звідки |
|-----------|------|--------|
| Веб-UI | вхід читача, маршрутизація | учасник Lab3, доріжка Lab4 |
| Сервіс підписок | `Subscription`, `Plan` | `er.mmd` Lab1; REQ-01..04 Lab2; Lab3/4 |
| Сервіс платежів | `Payment`, ідемпотентність | `er.mmd` Lab1; REQ-02/03/05 Lab2; callback Lab3 (ADR-001); Lab4 |
| Data Access | репозиторії над сутностями | усі сутності `er.mmd` Lab1 |
| БД | зберігання | концептуальна модель Lab1 |
| Планувальник | таймер REQ-12 | REQ-12 Lab2; обіцяний Lab4 «Поза обсягом» |

## Зовнішні інтеграції (required)

- **PaymentGatewayPort → Платіжний шлюз.** `authorizePayment` /
  `onGatewayCallback` — ті самі повідомлення, що в sequence Lab3. Порт/адаптер
  ізолює протокол зовнішнього шлюзу (ADR-001 lab4; варіант Gateway Adapter
  з ADR-001 lab3). Callback асинхронний, приймає Сервіс платежів.
- **MailPort → Поштовий сервіс.** Листи підтвердження, нагадування, повторне
  надсилання (REQ-12) [NFR-07]. Система фіксує спробу й не гарантує доставку.
  Пошта не актор (ADR-002 lab2), тож це required-порт, а не компонент-актор.

Межа системи: усередині — Веб-UI, обидва сервіси, Data Access, БД,
Планувальник і порти PaymentGatewayPort / MailPort; зовні — Платіжний шлюз
і Поштовий сервіс. Порти належать системі, зовнішні сервіси — ні.

## Provided-інтерфейси

Веб-UI надає читачеві вхід `submitSubscription` і сповіщення
(`subscriptionPending`, `showResult`, `showError`). API-операції сервісів —
ті самі, що в sequence Lab3: `createSubscription`, `activateSubscription`,
`cancelSubscription` (Сервіс підписок); `createPayment`, `findPaymentByTxn`,
`returnPaymentId`, `onGatewayCallback` (Сервіс платежів). Планувальник
надає тригерну операцію повторного надсилання (REQ-12) і вимагає MailPort.

## Критерії прийняття

- [ ] кожен компонент трасується до Lab1..Lab4 (таблиця вище)
- [ ] REQ-12 має носія: Планувальник
- [ ] NFR-07 має носія: MailPort → Поштовий сервіс
- [ ] шлюз — через порт/адаптер (ADR-001 lab4)
- [ ] provided/required інтерфейси визначені; без циклічних залежностей
- [ ] межа системи чітка (що всередині / що зовні)
- [ ] рендер синхронний з джерелом

## Поза обсягом

Мікросервіси, деплой, масштабування, черги брокера — не в моделі: це
експлуатаційні питання, а не компоненти предметної області. Фізична схема БД,
індекси й вибір СУБД — предмет курсу баз даних (як у Lab1). Внутрішня
реалізація шлюзу й поштового сервісу — зовнішні системи, моделюю лише порти.
