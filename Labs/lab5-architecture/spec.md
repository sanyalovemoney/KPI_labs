# Spec: Завдання 5 — Компонентна модель

## Намір

Показати архітектуру системи, у якій живуть усі чотири попередні моделі:
компоненти, їхні інтерфейси (provided/required), залежності та межа
системи. Архітектура — модульний моноліт: один деплой, чіткі внутрішні
модулі (див. ADR-001).

## Компоненти всередині межі системи

| Компонент | Трасування до ланцюга моделей |
|-----------|-------------------------------|
| Web UI | користувальницькі сценарії Lab2 (US-01..04) |
| REST API | вхід UC-01..09 |
| AuthModule | REQ-01, OAuth-інтеграція |
| CatalogModule | Book/Author/Genre з Lab1; UC-пошук |
| SubscriptionModule | User/Plan/Subscription; REQ-02..04; Lab4 |
| PaymentModule | Payment; адаптер до зовнішнього шлюзу; REQ-03/09 |
| LoanModule | Loan; Lab3-діаграма — це його внутрішній потік |
| ProgressModule | ReadingProgress; REQ-05 |
| ReviewModule | Review; REQ-06/10/12 |
| DataAccess (репозиторії) | по одному на сутність Lab1 |
| Database | ER-модель Lab1 |

## Зовнішні інтеграції (поза межею)

Платіжний шлюз (REQ-02/03), Поштовий сервіс (REQ-01/11),
OAuth/Identity провайдер (REQ-01), Search-індекс (опційно).

## Критерії прийняття

- [ ] Кожен компонент трасується до Lab1..Lab4 (таблиця вище — джерело
      істини для аудиту)
- [ ] Межа системи одним прямокутом: зовнішні системи поза нею
- [ ] Для кожної зовнішньої інтеграції — required-інтерфейс всередині
      (абстракція) і реалізація-адаптер
- [ ] Напрям залежностей: UI -> API -> модулі -> DataAccess -> DB;
      жодної зворотної стрілки і жодного циклу
- [ ] LoanModule залежить від SubscriptionModule (перевірка підписки),
      а не навпаки — згідно з Lab3
- [ ] Без DDL, без розгортання інфраструктури — лише компоненти

## Поза межами

Мікросервісний розклад, черги, кеші — ADR-001 свідомо відкинув на нинішньому
масштабі.
