Вимоги
Як здавати кожне завдання й що вважається сильною роботою. Рев'ю — ~5 хв: точка входу — DEFENSE.md.

ОБОВ'ЯЗКОВІ АРТЕФАКТИ (кожне завдання):
- spec.md (≤1 стор.): намір, сутності/кроки, критерії прийняття (з AI — це задача для AI; критерії фіксуються комітом, не лише в DEFENSE).
- Артефакт моделі + 1 рендер-діаграма (Mermaid / PlantUML).
- Аудит: топ-3 розбіжності (модель ↔ spec ↔ попередні моделі) + виправлення через зміну spec/критеріїв (не ручний патч).
- DEFENSE.md (1 стор.): точка входу для рев'ю.
- ADR на ключові рішення (за MADR).

ШАБЛОН DEFENSE.md:
1. Намір і критерії (1-2 речення).
2. Топ-3 розбіжності, які знайшов і виправив (проти пункту spec) -> коміт.
3. Ключове рішення - які альтернативи зважив і чому обрав цю (adr/…).
4. Перевірка: узгодженість із попередньою моделлю - як перевірив.

НАСКРІЗНА ВИМОГА: тримати узгодженим ланцюг моделей (дані -> вимоги -> взаємодія -> процес -> архітектура). Кожне завдання спирається на попередні й не суперечить їм.

ДВА ШЛЯХИ:
- Без AI: слід - це ваша історія рішень і самоперевірка першої версії проти spec.
- З AI: додатково повний слід промптів (ai/) і аудит виходу AI (топ-3 його помилок, які ви знайшли й виправили); для кожної розбіжності - посилання на промпт, фідбек-коментар і додаткову spec.

Обидва шляхи мають однакову планку якості та бюджет рев'ю. Оцінюється розуміння й захист рішень, а не інструмент.

ЧЕКЛИСТ «ГОТОВО»: DEFENSE (1 стор.) · spec (≤1 стор.) з критеріями · топ-3 розбіжності з комітами · артефакт + рендер через коміти · ADR · реалістична git-історія · чистий репозиторій.

(Повні версії — DEFINITION-OF-DONE.md і DEFINITION-OF-DONE-NO-AI.md — викладач надасть у репозиторії курсу.)

labs 1 
Мета: обрати домен і описати дані як модель сутностей і зв'язків (ER).

Артефакт (текст + рендер): ER-модель у декларативному синтаксисі (Mermaid erDiagram або PlantUML) — сутності, атрибути, зв'язки, кардинальності, первинні/зовнішні ключі. Рендер — ER-діаграма з опису. Без фізичної схеми БД (SQL DDL / ORM) — це предмет курсу баз даних. Без сполучних таблиць (напр. user_roles): чистий «багато-до-багатьох» — це зв'язок між сутностями; асоціативна сутність — лише коли зв'язок несе власні атрибути.

Що зробити:
• Обрати домен (напр. онлайн-магазин, бронювання, бібліотека), описати в README.md.
• spec.md: сутності, атрибути, зв'язки — словами; критерії прийняття (з AI — це і є задача для AI).
• Побудувати ER-модель декларативно; згенерувати erDiagram.
• Аудит: кардинальності, нормалізація, ключі проти spec.md; топ-3 виправлення через зміну spec/критеріїв (коміти), а не ручний патч.
• DEFENSE.md: чому цей домен, чому така нормалізація.

Ознаки відмінного виконання: кардинальності й ключі коректні; модель нормалізована; ER-рендер збігається з описом.

Типові помилки (часто зустрічаються):
• Критерії (напр. 3NF, типізовані id) названо в DEFENSE, але не зафіксовано в spec.md — у репозиторії їх «немає».
• Модель згенеровано ШІ, а подано як ручну; сам промт/задача до ШІ не збережені в репозиторії.
• Розбіжність виправлено ручним патчем діаграми замість зміни spec/критеріїв.
• Змодельовано сполучну таблицю (user_roles) замість зв'язку «багато-до-багатьох».
• Неузгоджені типи ідентифікаторів (десь string, десь number).
• Назви полів у діаграмі й spec розходяться (напр. price vs unit price).
• Недбалі коміти («fix», «тикав по клавіатурі»).
• Пункт «Перевірка» в DEFENSE не заповнено (для 1-ї роботи — це узгодженість spec ↔ модель).

labs 2
Мета: структуровані вимоги, сценарії використання і трасування.

Артефакт (текст + рендер): EARS-вимоги (WHEN <тригер>, система SHALL <реакція> / WHILE <стан>, …) + user stories + Gherkin-сценарії (Given/When/Then); матриця трасування «вимога-id ↔ сценарій/UC» як таблиця в Markdown. Рендер — Use Case Diagram (PlantUML / Mermaid) з ≥2 типами акторів, include/extend, узагальненням.

Що зробити:
• spec.md: ≥2 типи акторів (людина + зовнішня система/сервіс), головні цілі.
• Написати EARS-вимоги, user stories, Gherkin; побудувати use-case-діаграму.
• Матриця трасування: зв'язки багато-до-багатьох (не 1:1); позначити непокриті вимоги/UC.
• Аудит: EARS на двозначність; include/extend; звірити акторів і сутності з моделлю даних (Завдання 1); топ-3 розбіжності.
• DEFENSE.md: чому такі межі сценаріїв.

Ознаки відмінного виконання: вимоги в EARS однозначні й тестовані; трасування реально багато-до-багатьох; узгодженість з моделлю даних; є ≥1 непокрита вимога з поясненням.

labs 3
Мета: описати динаміку ≥1 ключового сценарію взаємодії.

Артефакт (текст + рендер): Sequence-діаграма в декларативному синтаксисі (Mermaid sequenceDiagram / PlantUML) — актори, основні компоненти/об'єкти, повідомлення з напрямком викликів, return-повідомлення, альтернативні/умовні гілки (opt/alt/loop). Рендер — діаграма з цього опису.

Що зробити:
• spec.md: обрати ≥1 UC із Завдання 2; учасники й кроки сценарію.
• Побудувати sequence-діаграму; реалістичні назви дій (submitOrder(), validateUser(), getBookList()).
• Аудит: об'єкти відповідають сутностям/сервісам ER-моделі (Завдання 1); є альтернативні/помилкові гілки; кроки збігаються з UC (Завдання 2); топ-3 розбіжності.
• DEFENSE.md: як діаграма деталізує UC і узгоджується з моделлю даних.

Ознаки відмінного виконання: діаграма деталізує обраний UC; учасники узгоджені з ER-моделлю; є альтернативні/циклічні гілки; назви викликів реалістичні.

labs 4
Мета: описати один бізнес-процес однією точною формою (без «двох нотацій»).

Артефакт (текст + рендер): Activity-діаграма (Mermaid flowchart / PlantUML activity) АБО машина станів (Mermaid stateDiagram-v2) для одного процесу — початок/кінець, дії, потоки керування, розгалуження (if/else), паралельні гілки (fork/join), ролі (swimlanes) за потреби. Рендер — діаграма з цього опису.

Що зробити:
• spec.md: процес, що деталізує UC із Завдання 2; кроки, ролі, розгалуження.
• Побудувати одну декларативну форму (activity АБО машину станів); згенерувати рендер.
• Аудит: повнота переходів, досяжність станів, коректність умов, паралельні гілки/join; звірити з UC (Завдання 2) і Sequence (Завдання 3); топ-3 розбіжності.
• DEFENSE.md: чому така структура станів/кроків.

Ознаки відмінного виконання: логіка повна (без недосяжних станів і «дір» у переходах); є ≥1 розгалуження й ≥1 паралельна гілка; узгодженість з UC/Sequence.

labs 5
Мета: модель архітектури — компоненти, інтерфейси, залежності й межі системи.

Артефакт (текст + рендер): UML Component Diagram у декларативному синтаксисі (PlantUML component / Mermaid) — компоненти (UI, API/Backend, сервіси, Data Access, БД), provided/required-інтерфейси, залежності, чітка межа системи, зовнішні інтеграції (Payment, SMS/Email, OAuth/Identity, External API…). Рендер — компонентна діаграма з цього опису.

Що зробити:
• spec.md: модулі (UI, API, сервіси, Data Access, БД) + зовнішні інтеграції.
• Побудувати компонентну модель; згенерувати діаграму.
• Аудит: кожен компонент/залежність трасується до попередніх моделей (дані, вимоги, взаємодія, процес); межа системи чітка; provided/required-інтерфейси визначені; топ-3 розбіжності.
• DEFENSE.md: як модель інтегрує весь ланцюг моделей.

Ознаки відмінного виконання: компоненти, інтерфейси й межі коректні; повна узгодженість з моделлю даних, вимогами, взаємодією та процесом; аудит присутній.
